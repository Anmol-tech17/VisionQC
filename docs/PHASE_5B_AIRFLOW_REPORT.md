## Architecture and Implementation Decisions

### Airflow Version and Executor
- **Version:** `apache/airflow:2.10.3-python3.12` — pinned for reproducibility.
- **Executor:** `LocalExecutor` — appropriate for a 2-thread CPU laptop. No Celery, Redis, or Kubernetes.
- **Metadata database:** SQLite stored at `/mnt/d/visionqc-airflow/data/airflow.db` — keeps Airflow data on **D:** as required.

### Separate Compose File
Airflow uses `docker-compose.airflow.yml` — separate from `docker-compose.yml` (inference API). This ensures:
- The inference API can run without Airflow.
- Airflow can run without the inference API container.
- No port conflicts (API: 8000, Airflow: 8080).

### Smoke-Test Mode (Default: ON)
The DAG defaults to `VISIONQC_SMOKE_TEST=true`, which overrides training to 1 epoch, batch 2. This prevents an accidental 1–2 hour CPU training run on every pipeline validation. Full training requires `VISIONQC_SMOKE_TEST=false`.

### DAG Design
The DAG (`visionqc_pipeline`) has 6 sequential tasks with XCom for metric passing:
1. `validate_inputs` — checks paths, configs, dataset, baseline metrics
2. `prepare_dataset` — verifies or regenerates YOLO dataset
3. `train_candidate` — runs `scripts/train.py` (smoke or full)
4. `evaluate_candidate` — runs `scripts/evaluate.py` and pushes metrics via XCom
5. `compare_with_baseline` — compares mAP50 against stored baseline JSON
6. `record_results` — writes `reports/airflow_pipeline_summary.json`

### Model Safety
- The existing `VisionQC-Detector@champion` is **never automatically overwritten**.
- The `finalize_experiment.py` script (which could promote a model) is **not invoked by the DAG**.
- The baseline evaluation JSON is read read-only; baseline metrics are never regenerated by the DAG.

### Storage on D:
- Airflow metadata DB: `/mnt/d/visionqc-airflow/data/airflow.db`
- Airflow task logs: `/mnt/d/visionqc-airflow/logs/`
- VisionQC reports (written by DAG tasks): remain in project `reports/` on C: (acceptable — project location not moved)

## Airflow Startup Commands
```bash
# Create D: storage directories first
wsl -d Ubuntu-D --user root -- mkdir -p /mnt/d/visionqc-airflow/data /mnt/d/visionqc-airflow/logs

# Start Airflow
wsl -d Ubuntu-D --user root -- bash -c \
  "cd '/mnt/c/Users/dell/OneDrive/Desktop/MLOPS CP/VisionQC' && \
   docker compose -f docker-compose.airflow.yml up -d"

# Access Airflow UI: http://localhost:8080
# Credentials: admin / admin
```

## Airflow Shutdown
```bash
wsl -d Ubuntu-D --user root -- bash -c \
  "cd '/mnt/c/Users/dell/OneDrive/Desktop/MLOPS CP/VisionQC' && \
   docker compose -f docker-compose.airflow.yml down"
```

## Triggering the DAG Manually
```bash
# Via CLI inside the container
wsl -d Ubuntu-D --user root -- docker exec visionqc-airflow \
  airflow dags trigger visionqc_training_pipeline

# Or via Airflow UI: http://localhost:8080 → DAGs → visionqc_training_pipeline → Trigger DAG
```

## Known Limitations
1. **Full pipeline not executed:** Training a YOLO model for even 1 epoch takes ~2 minutes on this CPU; a 40-epoch full run takes 1–2 hours. Smoke-test mode validates pipeline structure only.
2. **Airflow pip install at startup:** The Airflow image installs `ultralytics`, `mlflow`, etc. at container start. This adds ~5 minutes to first launch. A custom Airflow image would be faster for repeated use.
3. **SQLite Airflow DB:** Not recommended for production multi-worker setups, but appropriate for LocalExecutor on a single laptop.
